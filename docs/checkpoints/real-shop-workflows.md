Existing docs describe the old workflow; they will be synchronized with verified implementation, not preemptively marked complete.

1. Persisted flow is QUEUED → PREPARING → READY → COMPLETED, driven by history triggers. DRAFT is browser-only. Prior-day system cancellation covers unfinished rounds; history and sale rows are immutable.
2. Kitchen currently exposes queued/preparing work and START/READY; Dispatch reads READY and completes it. No Dispatch-specific persistence table exists.
3. Bills own DINE_IN/TAKEAWAY and reference. Kitchen omits this metadata. Platforms have no Bill/service type; preserve their channel and external reference rather than inventing Dine-In/Parcel classification. Legacy unknown service remains explicit.
4. Effective revisions preserve stable original line IDs even for replacements. Serving must pin effective revision and line identity and prevent later amendment after any serving event.
5. Parcel completion requires zero collection/refund due; Dine-In may complete unpaid. Bill closure is separate, explicit and settlement-gated. Confirmation plus optional Cash/UPI collection is already atomic.
6. OrderCart success clears rows but leaves checkout locked and returns an exclusive success panel until New Order. PlatformPos also blocks on confirmed state. Both retain exact uncertain requests in sessionStorage; keep recovery semantics.
7. CartSurface computes a viewport height; .order-cart is sticky/max-height bounded and .cart-items scrolls. Desktop should instead use page flow; mobile should have one whole cart-dialog scrolling surface, never nested line scrolling.
8. Proposed migration 022: additive append-only serving events with line/order/actor/revision, signed quantity, correction reason, expected served quantity and actor/request idempotency. Direct actual fulfillment to COMPLETED from active/legacy states; preserve old lifecycle history. Backend quantity/revision/state/payment checks under existing restaurant lock; database constraints/triggers independently protect invariants.
9. Proposed Kitchen commands: serve/correct a Dine-In line and fulfill Parcel/platform/legacy round, plus operational history. Add kitchen.fulfill to OWNER/MANAGER/KITCHEN/DISPATCH and kitchen.read to DISPATCH; no financial/menu/admin grants. Remove Dispatch navigation, redirect authorized legacy route. Keep compatible backend structures.
10. Risks: serving vs amendment/cleanup races, stale/double submission, legacy READY work, unknown service, accidental stale Bill association, constrained-height cart. FIFO remains chronological display/NEXT guidance, not a block on serving later-ready dishes. Corrections only while nonterminal; completion cannot be undone.
11. Sequence: POS natural scrolling/reset/Parcel terminology; serving domain/migration/API and DB tests; unified Kitchen/read models/RBAC; responsive/browser regressions; documentation and reviewed migration/deployment plan. No merge until complete checks pass.
