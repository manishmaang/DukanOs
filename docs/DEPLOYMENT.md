# Deployment planning — not a deployed configuration

Status: **blocked for real restaurant production** pending the release gates in [Production readiness audit](PRODUCTION_READINESS_AUDIT.md). This document is a plan, not evidence of deployment, backup automation or recovery certification. No AWS resource, infrastructure configuration or synchronization is supplied by this milestone.

## One restaurant, one writable authority

For shop operation, recommend a local server containing the compiled React assets, NestJS API, PostgreSQL and persistent media. Devices use one HTTPS origin over the shop LAN. WAN loss must not move writes to a second independent database. Cloud staging is a separate disposable environment; it must not send real owner reports or contain an unprotected copy of restaurant credentials/data.

A cloud-only production instance requires internet for every shop operation and therefore cannot satisfy the current continuity requirement. A future cloud production installation is technically possible, but it cannot simultaneously operate as a writable copy of the local restaurant without a separately designed synchronization/failover milestone.

## Environment matrix

Secrets belong in the actual protected environment file or supervisor secret injection, never `.env.example`, browser settings, command-line arguments or Git. The current npm entry points require a root `.env` file even when process environment supplies the values. Use a service-owned file outside a versioned release, protected with mode 0600; a controlled link at the expected path is one possible future deployment arrangement. Process environment takes precedence over Node's `--env-file` values. Avoid printing effective configuration.

Current generic startup errors omit secret values but offer limited diagnosis.

## Build and release shape

Repository requires Node >=22.12; audit used Node 24.13.1 and PostgreSQL 16.15. Choose a supported, patched Node 24 LTS and PostgreSQL 16 release and rerun the suite on those exact versions. Do not interpret the open-ended engine constraint as certification of every future version. [Node's production release guidance](https://nodejs.org/en/about/previous-releases) recommends supported LTS lines.

Development uses `npm ci`, `npm run db:up`, `npm run db:migrate`, `npm run dev`; see README. This Compose definition provisions PostgreSQL only. There is no application Dockerfile, production Compose or CI deployment pipeline in this repository.

Planned release sequence, **not executed against the restaurant by this audit**:

1. Build a versioned release with lockfile-based `npm ci`, `npm run check` and required integration/browser verification. Builds require dev dependencies; do not omit them before compiling. Native Sharp binaries must match target OS/architecture. Preserve apps/api/dist, apps/web/dist, compatible runtime dependencies, package manifests, migrations and migration runner in their expected layout.
2. Confirm recoverable database/media/config backup and change window. Stop writes/workers where migration/backup consistency requires it. Do not use automatic demo seeds or owner bootstrap on an existing restaurant.
3. With the intended migration role and correct database, run `npm run db:migrate`. Make its successful exit an explicit prerequisite for startup, not an independent ignored command. All pending migrations share one transaction and a checksum ledger; do not edit applied SQL or use `docker compose down -v`.
4. Start the compiled API under a non-root supervisor, with NODE_ENV=production and protected environment, persistent media, TLS proxy, restart policy, log retention and clock synchronization. Existing `npm start` runs the compiled API from its workspace and loads `../../.env`; it does not build or migrate. Prefer a direct Node child under the chosen supervisor with equivalent environment/release paths and tested SIGTERM forwarding.
5. Gate traffic on migration checksums/expected version, web assets, readable/writable media and database readiness. Check `/api/health` (process) and `/api/health/ready` (SELECT 1 only), then perform authenticated critical-read and controlled staging workflow checks. These endpoints alone do not establish complete readiness.
6. Rehearse restart, failed migration, expired session, missing disk/database, overdue worker catch-up, WAN outage and graceful shutdown on staging/local test hardware before the first real shift.

Nest shutdown hooks stop scheduler intervals, await active work and close the DB pool. SMTP runs outside DB transactions but worker shutdown may await multiple bounded transport attempts. Choose and measure the supervisor grace period; a forced stop can leave a reclaimable email lease and uncertain delivery. No end-to-end supervisor/system-reboot test was performed here.

## HTTPS, origin and network requirements

Use one origin for browser assets and `/api`, on cloud and LAN. Production authentication cookies are Secure, HttpOnly, SameSite=Strict and scoped to `/api`. A non-localhost `http://192.168...` shop URL is **not** a valid production authentication deployment. Provision trusted local HTTPS and stable local DNS/reservation, with certificates already trusted by devices and usable while WAN is down. Public certificates can continue to work offline until expiry; renewal requires planning. Do not disable Secure or use NODE_ENV=development as the shop solution.

No CORS is enabled; no wildcard origins are present. Cross-origin credentialed frontend hosting is not configured. Preserve cookies, mutation header `X-DukanOS-Request: 1`, all required methods, query strings and original API status codes through a proxy. Do not cache authenticated API responses or rewrite API errors into index.html. Apply request/upload limits with multipart overhead (application image payload limit 5 MiB), bounded proxy timeouts, secure response headers and access-log redaction. Never log Cookie, Set-Cookie, Authorization, bodies, passwords or connection URLs.

Express currently trusts no proxy. Behind a proxy its IP-based login limiter sees the proxy address, sharing a 60-attempt/15-minute budget. A future narrowly trusted, sanitized forwarding configuration and tests are required; do not blindly trust arbitrary X-Forwarded-For or set trust proxy=true. Patch the audited proxy dependency first.

Keep API origin and PostgreSQL inaccessible to general internet clients; restrict inbound access at both host and cloud firewall layers. Separate migration/schema ownership from runtime database permissions and test triggers/CLI maintenance with those grants. Owner recovery intentionally accepts loopback PostgreSQL only; RDS requires a reviewed local tunnel/recovery procedure preserving certificate verification, not removal of the loopback guard.

Daily generation failure skips delivery work in that worker cycle. Multiple HTTP processes can share locking, but each has its own 5-connection pool and needs the same durable filesystem. Keep one API process initially; do not scale across independent local upload disks.

Operational audio needs an explicit touch gesture, unmuted device and active usable browser. Each browser/tab may sound independently; do not promise exactly one restaurant-wide alarm. Keep visual alerts and staff procedures. Physical-device sound/background/keyboard checks remain required.

## Storage, backup and rollback

A **database backup** contains tables, constraints, functions, permissions, migration ledger, users/session hashes, immutable financial/audit records, report versions/settings/jobs/attempts and image metadata. It does not contain image bytes.

A **full DukanOS backup** additionally needs:

- Entire persistent `DUKANOS_DATA_DIR/uploads/menu` and `uploads/expenses`, including referenced images and receipts retained after expense voids.
- Protected runtime configuration, database-role/grant setup, certificate/trust material and recovery secrets stored encrypted with separate restricted access.
- Release commit, lockfile, migration checksums and a compatible deployable artifact or offline installation cache. Git tags alone are not data recovery.

Menu uploads are normalized to 1024×1024 WebP quality 82, receipts to 2400×2400 WebP quality 90, without enlargement. Both reject unsupported MIME/content, animation, >24MP or >5MiB input. Generated UUID paths and authenticated reads protect file access. Default new directories are 0700 and files 0600; verify existing directory ownership/modes separately. Monitor free space/inodes and backup both directories; no S3 runtime adapter, disk quota or backup scheduler exists.

Plan encrypted off-device copies with retention and alerts, including an offline/local copy when internet is down. Choose explicit recovery-point/recovery-time objectives with the owner before operation; a once-daily copy potentially loses a whole shift. A coordinated paused-write backup of PostgreSQL plus uploads is the simplest initial consistent recovery point. Capture any DB roles needed separately. Restore first into an isolated environment with SMTP/automatic outbound delivery disabled; verify money totals, snapshots, image references, users, migration checksums and pending jobs before reconnecting devices. Never let the old and restored databases accept writes simultaneously. Recovery to an older point can lose later payments/idempotency keys and queued email acceptance history; reconcile real-world receipts and sent messages before reopening. Restore drills and automation remain unimplemented.

Rollback is a compatibility decision, not `git checkout` plus restart. Database migrations have no automatic down path. Prefer a reviewed forward fix; restore a compatible database+media+configuration set only under controlled recovery and reconcile all later real-world transactions. Never erase production history to make older code boot.

## Cloud staging recommendation

Start with one small EC2 Linux VM, a TLS reverse proxy, one compiled application process and an encrypted persistent volume for uploads. Use isolated PostgreSQL 16 (on that VM for inexpensive disposable staging, or RDS when rehearsing the final managed-DB path). Restrict access, use synthetic data, and disable external SMTP or use a local capture relay. Losing this environment must not interrupt the restaurant. Choose exact instance sizes after a target-host test; current laptop measurements do not establish cloud sizing or prices.

## Local shop production recommendation

Planning baseline: dedicated 64-bit machine with SSD, approximately 4 modern CPU cores and 8GB RAM; 16GB adds build/image/report headroom. A 256GB or larger SSD is a reasonable starting capacity, subject to measured upload growth/retention. These are engineering estimates, not a hardware benchmark or purchase recommendation. Prefer wired Ethernet for the server, stable LAN address, reliable access point, UPS for server/router/access point, automatic reboot/service startup, correct clock after power loss, and restricted physical/admin access.

| Option          | Benefits                                                            | Checks before choosing                                                                                                                                           |
| --------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mini PC         | Compact, low operational footprint, suitable dedicated host         | SSD health, cooling, Linux support, Ethernet and BIOS power-loss restart; external UPS required.                                                                 |
| Existing laptop | Can reuse hardware; healthy battery bridges short server power loss | Battery condition, cooling, disable lid/sleep interruptions, wired adapter reliability; router still needs UPS. Do not mix restaurant authority with casual use. |
| Desktop         | Repairable/upgradable, often already available                      | Electricity/space, dust/heat, SSD, UPS sizing and automatic restart.                                                                                             |

Services: local HTTPS proxy + compiled app/workers, local PostgreSQL, persistent media volume, local logs/monitoring and off-device backup target. All depend on power/SSD/LAN; SMTP alone waits for WAN. Never expose this database through router port-forwarding. Rehearse five-device use (two POS, Kitchen, Dispatch, owner), real camera/keyboard/speaker behavior, full power recovery, disk failure restore and WAN-disconnected fresh login/order/payment/Kitchen/Dispatch before opening.
