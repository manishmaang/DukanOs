# Production deployment readiness audit — 2026-10-07

The original audit below is preserved as historical evidence. See the [2026-10-09 hardening follow-up](#2026-10-09-hardening-follow-up) for the current repository status.

## Verdict and scope

**Not ready for real restaurant production.** The business foundation has substantial passing transactional coverage, but release gating, credentials, TLS, recovery and operational verification remain incomplete. This is a blocking audit of source baseline `5b252c88223f7be0c0910ea01be29b06da12a8d6`, not a deployment approval or penetration test.

No AWS resources, production infrastructure, application behavior, dependencies, business features or applied migrations were changed. The live migration ledger/settings were read only. Operational experiments used uniquely named temporary PostgreSQL schemas and temporary media. External SMTP was disabled; only the integration suite's explicit loopback capture transport was allowed. See [Deployment plan](DEPLOYMENT.md) for environment inventory, architecture, worker schedules, backup scope and release procedure.

### Dependency evidence

`npm audit --omit=dev --json` ran against the current lockfile; no install/update/fix command ran. Four affected-package findings include a transitive duplicate for Nest's adapter, not four independent exploits:

- `proxy-addr` <2.0.8, upstream CRITICAL: incorrectly configured IPv4-mapped IPv6 trust subnets can accept spoofed client IPs. Current Express trust proxy is disabled, so the documented exploit condition was not found. Patch before introducing trusted proxies. [Reviewed advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h).
- Sharp <0.35.5, upstream HIGH, bundled librsvg issue. DukanOS rejects SVG format before image output, but calls Sharp metadata on bytes first; MIME rejection alone is not proof of native-parser immunity. No exploit test was performed. Update native dependency and retest supported-image processing. [Reviewed advisory](https://github.com/advisories/GHSA-wq5f-xc86-pv6w).
- Multer 2.2–2.3, upstream MODERATE, aborted disk-storage uploads can leave files. DukanOS uses bounded memoryStorage, so that diskStorage condition is not present. Update the stale 2.3 override/lock after review; Nest platform-express also appears because it depends on Multer. [Reviewed advisory](https://github.com/advisories/GHSA-3pph-fpjx-jg34).

Registry status is time-sensitive; repeat the scan on the actual release. Build/tool dependencies and OS/native packages need release maintenance too; this production scan is not a full supply-chain assessment.

## Authentication, API and secrets

Reviewed controllers, global guard/input boundary/error filter, auth and password services, local recovery script and integration tests. Passwords use salted asynchronous scrypt N32768/r8/p3 and timing-safe comparison; length12–128. Sessions are random256-bit opaque cookies, SHA256 in PostgreSQL, expire12h without sliding refresh. Password/access changes revoke all target sessions, logout revokes the current session. Every request resolves live capability unions; sensitive mutation transactions recheck session/capabilities after locks. OWNER/MANAGER exclusivity and operational combinations remain enforced by domain and database.

Production Set-Cookie was directly checked on the isolated API: Secure, HttpOnly and SameSite=Strict present. The Node test manually forwarded the cookie over loopback; this **does not verify a browser HTTPS deployment**. LAN HTTP on a normal shop address is unsuitable. Missing or misspelled NODE_ENV silently removes Secure; require validated deployment configuration. Cross-origin CORS is disabled, and unsafe methods require the custom mutation header including login. Same-origin hosting is intentional, not missing wildcard CORS.

Login counters persist: ten attempts/account and sixty/source IP per15min; successful logins count too. Current-password verification has its own throttle. Unknown-user hashing avoids an easy timing shortcut. No public registration/recovery endpoint, external identity dependency, MFA or device-session dashboard exists. Local recovery requires exact active OWNER, hidden input/stdin and loopback database, revokes sessions and audits a reason. OS/DB admin access remains a trusted recovery boundary.

Tracked-path checks found only `.env.example`, no committed `.env`, PEM/key or `.aws` path in available Git history. A current tracked-file scan for common private-key/AWS/GitHub token patterns found no matches. Runtime code/log call sites and frontend sources were inspected; no deliberate credential/body logging or compiled external API origin was found. This is a limited scan, **not proof that every historical blob or arbitrary secret format is clean**. Real `.env` credentials were not printed or copied into documentation. Database and SMTP URLs/passwords must remain out of startup/proxy logs; current generic messages protect privacy but hinder diagnosis.

## Database, migrations and financial invariants

Read-only check: 18 local migration records, 18 repository SQL files, all SHA256 checksums matching, latest `018_daily_owner_reports.sql`. PostgreSQL16.15; current database size approximately27.6MiB including temporary activity at measurement time, not a production sizing basis. Runtime role superuser=true; max_connections100, shared_buffers128MB, work_mem4MB. These are current local defaults, not production tuning recommendations.

Migration runner serializes with transaction advisory lock742019321, verifies file order/identity/checksums and commits all pending SQL/ledger together; existing migration tests cover failures and preservation. No migration ran against the operational schema in this audit. Application startup neither seeds demo business data nor runs migrations automatically. Bill rollover intentionally modifies eligible old OPEN sessions when a real server starts; do not confuse that expected worker behavior with migration resets. Audit fixture startup used its own schema.

The application pool has five connections per API process; additional CLI/test clients use independent connections. Restaurant mutations generally serialize on742019323; staff access uses742019322; report generation742019324. Financial/operational writes revalidate under locks and use transaction rollback, restrictive FKs, checked numerics and actor/request fingerprints. Five devices do not need five dedicated persistent database connections. No single-browser assumption was found; write races are explicitly tested. More API replicas do not remove the common write lock and require shared media.

Reviewed BillsService, Orders orchestration/lifecycle, amendments, expenses, effective reporting views and migrations008–018 with regression evidence:

- Confirmation resolves Counter availability/prices server-side, snapshots names/tax/amounts, allocates unique business-date token and commits optional Bill receipts atomically. No fake money for Pay Later; cancelled tokens are not recycled.
- Collections/refunds are append-only, bounded by locked current due/refund entitlement; CASH-only customer refunds are protected in API and DB. Actor/request identity prevents duplicate replay and conflicts on changed intent. Concurrent tests cover double collection/refund and rollback.
- Original order items/totals remain immutable; queued amendments append full revisions and audit, and effective views determine current totals. Menu/tax changes do not alter earlier snapshots. Payments do not change Kitchen lifecycle.
- Historical rollover closes ordering sessions, not balances. It preserves Kitchen progress; Takeaway requires amount_due and refund_due zero. Historical Dine In reminders pause; legitimate late financial reconciliation remains permitted.
- Expenses are separate from customer money, immutable except audited void metadata, with category snapshots and receipt retention. Voids restate live reports; they are not invented supplier refunds.
- Sales use effective food/Bill-date semantics, receipts/refunds their actual transaction dates. Daily versions freeze their source snapshot; regeneration creates another version.

No tested path double-collected/refunded, reset tokens, bypassed tested capabilities or rewrote immutable financial/report facts. Configuration changes cannot reprice stored sales, but timezone/clock changes affect future dates and live time-window reporting; secure the host clock and control config changes. Database superuser misuse can bypass triggers, and restoring an older backup can lose idempotency/history; these are material deployment boundaries.

## Workers, daily reports and alerts

[Deployment worker inventory](DEPLOYMENT.md#worker-and-alert-operations) gives exact startup/schedules/locks/failure paths. No separate reminder/timer server scheduler exists; frontend polling renders durable absolute timestamps.

Daily report generation is a consistent repeatable-read snapshot with date/version uniqueness and immutable UPDATE/DELETE triggers. Later corrections change live reports only. Explicit regeneration records reason/actor as v2+; queued/resend jobs bind a fixed report UUID. Integration tests exercised historical expense changes/voids, parallel regeneration, retry/replay and SQL immutability. v1 remains v1.

Worker catch-up cursor survives downtime; no SMTP dependency for snapshots or restaurant writes. Email configuration OFF/blank host does not crash the app. Auth/connection failures get sanitized retry codes, SMTP runs outside business transactions, and jobs retain recipient/attempt history. Invalid partially configured SMTP can fail bootstrap. Temporary recipient rejection classification needs M1 correction. Generation failure also postpones that cycle's delivery. No worker-freshness health signal exists.

Remote SMTP enforces validated TLS/STARTTLS; plaintext is allowed only for loopback relay/tests. No protocol logging, external attachments or email-render-time requests. Recipients/settings/send actions are capability restricted. SENT means provider acceptance, not inbox delivery; failure after acceptance can duplicate a recovered send. SMTP is the only intentional external runtime service; its outage must never authorize a second financial action.

Known cached reminder/timer deadlines can continue rendering and sounding during API failure, but fresh authentication/reload needs the local backend. Reconnect replaces state and clears ineligible alerts; rollover suppression cannot be guessed safely while offline. Sound needs a gesture and usable browser; sleeping/closed pages cannot guarantee alarms. There is no push, OS alarm or cloud scheduling guarantee.

## Storage and frontend

Both image services validate MIME against decoded format, bound input/file/pixels/pages, strip metadata through WebP output, generate UUID names, and use private filesystem modes. No client-controlled directory/filename is accepted. Menu replacement deletes obsolete files only after commit; expense receipts remain attached even when voided. Cleanup is explicit/dry-run, 24h grace and protected references, not a startup task. DB+filesystem are compensating operations, not one atomic distributed transaction. Existing directory permissions and disk capacity need deployment checks.

Current production frontend has relative same-origin APIs, bundled CSS/JS, local fonts/system styling, local authenticated images and generated Web Audio. Source search found no external runtime HTTP/WS URLs. Browser suites block external page requests. Installation/build/package downloads and SMTP need WAN; ordinary installed local POS/Kitchen/Dispatch/financial work does not. This is **LAN continuity**, not disconnected browser writes or cloud/local synchronization.

Production API serves apps/web/dist only if it exists. Hash routes require no server-side business route rewriting; preserve API 404s. Separate static hosting requires same-origin API routing. No frontend source or design was changed in this audit.
